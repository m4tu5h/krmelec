## 2026-10-12 — From reading one PDF to finding today's menus

Goal: build a simple lunch-menu app for nearby restaurants in Bratislava, while learning and documenting the process step by step.

### 1. Start small in a notebook

An initial Python agent and notebook were scaffolded, but the implementation moved too quickly for the learning goal. We reset the notebook and rebuilt it one code cell at a time. The notebook is now the active workflow; the earlier `menu_agent.py` prototype is not called by it.

We chose uv for environment and package management. VS Code's notebook kernel uses the project's `.venv`. Installing `ipykernel` resolved the initial “requires the ipykernel package” error.

### 2. Try SME as a source

We requested a restaurant menu using `httpx`. SME returned HTTP 403 with a “Security Verification” HTML page rather than menu content. This established that basic HTTP fetching was blocked in our experiment; it did not establish that all agents or browser access are blocked. Earlier research-tool fetches had returned HTTP 402.

We switched to the restaurant's own website instead of attempting to bypass verification.

### 3. Read Spilka's PDF

A direct Spilka menu-PDF URL returned HTTP 200. Printing `response.text` displayed PDF internals because PDFs are binary files. We saved `response.content` as a PDF, opened it in VS Code with a PDF extension, and used `pypdf.PdfReader` to extract its text.

The PDF contained readable text, so OCR was unnecessary for this example. An initial `gpt-4.1-mini` request turned that text into a readable menu. The user compared the answer with the PDF and confirmed that dates, dishes and prices matched.

### 4. Discover menus automatically

Direct PDF URLs can change each week. We changed the workflow to supply base restaurant websites and let the model find the current menu.

The notebook now uses the OpenAI Responses API with `gpt-5.5` and the hosted `web_search` tool. Each restaurant has its own allowed-domain filter; live access is enabled and `tool_choice="required"` requires tool use. The requested date is calculated in `Europe/Bratislava`.

Spilka's web-search experiment worked according to the user. We then added Centrálna Klubovňa and ALDA. Restaurant configuration separates `name`, `address`, `website` and `domain`, with branch identity included in the prompt.

### 5. Persist the results

Initially, `menu_results` existed only in notebook-kernel memory. We added a save cell that writes `menus.json` at the project root. The first saved format contained long Markdown answers, which was awkward for an app to filter.

We replaced it with a flat `meals` array using Pydantic models and Structured Outputs. Each meal has:

- `name`, `restaurant`, `address`
- `price_eur`, `portion`, `source_url`
- `soups`: possible soup options, each with `name`, `portion`, `additional_price_eur`
- `labels`: Slovak filtering attributes

The file also stores `requested_date` and `saved_at`. Restaurant identity is supplied by our configuration rather than generated by the model.

Original Markdown answers were preserved in `data/raw-menu-results.json` before migration. Existing results were converted locally without paid API calls. The user subsequently reran the structured extraction and save cells; the current file contains 17 main meals across the three restaurants, including soup options.

### 6. Define soup prices and labels

A soup's `additional_price_eur` is its surcharge with the main meal, not its standalone price. Explicitly included soup uses `0`; unknown surcharge uses `null`; no confirmed options uses `[]`. The agent is instructed to respect pairing restrictions rather than assume every soup accompanies every main.

Allowed labels are `cestoviny`, `bravčové`, `hovädzie`, `hydina`, `šalát`, `ryby`, `syr`, and `zelenina`. Multiple labels are allowed. They describe the main meal, excluding optional soups and minor garnishes. Uncertain labels are omitted; labels are not dietary certifications. For example, the saved Segedínsky guláš has no meat label because its description does not explicitly identify the meat.

### Current operation

1. Load the local `.env` and create the API client.
2. Define the restaurants.
3. Define the structured result models.
4. Search each restaurant and collect structured meals.
5. Save the combined meals to `menus.json`.

The search cell incurs model-token and web-search charges. A request can perform multiple searches. The save cell makes no API calls and automatically replaces the entire JSON file on disk. It does not preserve history. Running search alone does not update the file; saving alone uses results already in memory.

After external notebook edits, reopen the file if VS Code shows a save conflict, preserving any personal unsaved edits first. Rerun changed definitions in order because the kernel may still hold old variables.

### Validation and limitations

Python-cell syntax, saved-meal schema validation, and the save/load flow were checked locally. Simulated API responses exercised structured collection and exclusion of mismatched dates. These checks made no paid requests. They do not verify the accuracy of live search results.

The notebook accepts meals only when the returned confirmed date matches the requested date and date evidence is present. A model can still misread a source or generate incorrect evidence, so review prices, date evidence, source links, soup pairings and labels against the original menus. Not every saved meal has been independently verified by a human.

Unverified dates produce no meals for that restaurant. The flat file currently does not distinguish a missing restaurant menu from one with no meals. Search can miss newly published or inaccessible menus. There is no scheduled collection, history, database or web app yet. The earlier Python prototype and its configuration remain separate from the active notebook.

Next: review the structured results and then build a simple page that reads the saved JSON and filters by restaurant, price and labels. Collecting once daily will let the app reuse saved results without calling the agent for each visitor.
